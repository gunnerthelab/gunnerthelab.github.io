## 2026-07-11 - S1-push: new-story push alerts for the installed site PWA

- **What changed and why:** The site PWA (gunnerthelab.com) had no way to notify its own installed users when a new story publishes - that pipeline only ever reached the StoryReader reader app (app.gunnerthelab.com). Added a real `push` handler to the site's service worker plus an opt-in "Get new story alerts" button on the stories index page. Subscriptions are sent to storyreader-gunner's existing worker (`POST https://app.gunnerthelab.com/api/push/subscribe`, body `{ endpoint, p256dh, auth }`, header `x-requested-with: storyreader`) so site subscribers ride the exact same fan-out as the app: `worker/src/routes/admin.ts`'s `/api/admin/publish` route (called by `tools/publish.mjs` after every publish) sends a payload-less push to every row in `push_subscriptions`, with no brand filtering needed since gunner and holdfast are separate Workers on separate D1 databases (`wrangler.jsonc`).
- **Files touched:**
  - `public/sw.js` - added a `push` event handler (parses payload JSON defensively, but the pipeline above sends an empty body today, so it always falls back to a generic "New story from Gunner the Lab" notification; forward-compatible if a real payload is ever added). Removed the vestigial notification-on-every-`activate` code (fired on every deploy, not just story publishes) and the dead `NEW_CONTENT` `postMessage` (no listener anywhere in the codebase - confirmed via grep). The existing `notificationclick` handler was already generic enough to reuse as-is.
  - `src/components/PushAlerts.astro` - new component: feature-detects Push/Notification support, handles the iOS-Safari-requires-home-screen-install case (WebKit does not expose `PushManager` in a plain tab - confirmed via search, not just assumed), reflects subscribed/blocked/unsupported state, and gracefully degrades on a failed subscribe (rolls back the local browser subscription and shows a status message rather than claiming success it can't back up).
  - `src/pages/stories/index.astro` - mounted `<PushAlerts class="mt-6" />` in the header, under the "read in order" link. Deliberately NOT in the global Footer: the `/app` page already pitches the reader app's own "New-story alerts" feature, and both prompts fighting for attention on the same page would be confusing.
- **CORS status - READ BEFORE relying on this feature working today:** storyreader-gunner's worker has **no CORS handling anywhere** (no `hono/cors`, no manual `Access-Control-Allow-Origin`, no OPTIONS route) - confirmed by reading `worker/src/index.ts` and every route file, read-only, nothing was changed there. The subscribe request requires a custom header (`x-requested-with`), which forces a browser preflight; with no OPTIONS handler the preflight 404s and the browser blocks the POST. **Net effect: today, clicking the button successfully creates a local push subscription and requests notification permission (neither of those touch the worker and both work fine), but the POST that tells the worker about it fails, gets caught, and the local subscription is rolled back - the button reverts and shows "Couldn't turn on alerts right now."** This is expected with the current worker, not a bug in this commit.
  - **Minimal worker patch needed** (not applied - out of scope, another agent owns that repo and was actively pushing to it during this session): in `worker/src/routes/push.ts`, add `hono/cors` scoped to that router only, e.g. `push.use('*', cors({ origin: ['https://gunnerthelab.com', 'https://www.gunnerthelab.com'], allowMethods: ['POST', 'OPTIONS'], allowHeaders: ['Content-Type', 'x-requested-with'] }))` before the route handlers. No credentials flag needed - subscriptions are anonymous (`loadUser` is optional in `push.ts`). Hono ^4.6.0 is already a dependency, `hono/cors` needs no new package. Keep it scoped to the push router (not global `app.use`) so `/api/auth`, `/api/admin`, etc. stay cookie-only/same-origin.
- **Commands / tests run and results:** `npm run build` passed (47 pages) both before and after formatting. `npx astro check` found pre-existing errors in `BaseHead.astro` (gtag/dataLayer globals, one implicit-any - not touched, not introduced by this session) - not gating (not part of `npm run build`) but used it anyway to catch real bugs in the new script, which it did (missing param types, an arity mismatch calling `render()`, and a TS 5.7 typed-array generics issue on `applicationServerKey`); all fixed, `PushAlerts.astro` now has zero `astro check` errors. `npx prettier --write` on all three touched files; `--check` clean after. Manually verified `dist/sw.js` contains the `push` listener and `dist/stories/index.html` contains `push-alerts-button` after build.

- **Blockers:** The worker patch above. Until it ships, this feature is fully built and gracefully inert (no broken UI, just never successfully subscribes anyone).

## 2026-07-11 - A1-site: PWA update toast + stale-cache fix

- **What changed and why:** The installed site PWA (gunnerthelab.com, added to home screen on iPhone/iPad) was serving stale cached content. Root cause: `CACHE_NAME` in `public/sw.js` was a static string, so the service worker script was byte-identical across deploys and the browser never detected an update, never re-ran `install`/`activate`, and never refreshed the precached shell. Fixed the root cause with per-deploy cache versioning and added a visible, user-confirmed update flow so an already-open tab is never swapped out from under the user silently.
- **Files touched:**
  - `astro.config.mjs` - new `swCacheBuster` integration; an `astro:build:done` hook stamps `dist/sw.js`'s `CACHE_NAME` with `GITHUB_SHA` (or a build timestamp for local builds). Only the `CACHE_NAME` string literal is touched so the explanatory comment above it stays readable.
  - `public/sw.js` - `CACHE_NAME` now carries a `__CACHE_VERSION__` placeholder (replaced only in the build artifact, source stays deterministic); `install` no longer auto-calls `skipWaiting()` (lets a real update sit in the "waiting" state instead of taking over immediately); added a `message` listener for `{type:'SKIP_WAITING'}`. `activate`'s old-cache cleanup was already correct and is unchanged.
  - `src/components/BaseHead.astro` - replaced the old "activated-state" banner with a toast keyed off `updatefound`/`registration.waiting`. Tapping it posts `SKIP_WAITING` to the waiting worker; the page reloads once on `controllerchange` (once-flag guard). Added a `visibilitychange` nudge that calls `registration.update()`, since iOS home-screen PWAs rarely re-check for updates on their own.
- **Commands / tests run and results:** `npm run build` passed (47 pages). Ran it twice locally and confirmed `dist/sw.js` got a different stamped `CACHE_NAME` suffix each time. `npx prettier --check` clean on all three touched files after `--write`.
- **Branch:** main - committed: yes - pushed: yes (see git log for hash).
- **Blockers:** None.
- **Exact next steps:** None required for this task. Optional future polish (not done, out of scope): reconsider whether the browser `Notification` ("New stories have been published!") in `sw.js`'s `activate` handler still makes sense now that `activate` only runs after a user-confirmed update (or true first install) rather than automatically on every deploy.
